### Aggregation-Pipeline ($lookup)

```javascript
db.recipes.aggregate([
  // Join mit categories
  {
    $lookup: {
      from: "categories",
      localField: "category_id",
      foreignField: "_id",
      as: "category"
    }
  },
  { $unwind: "$category" },

  // Join mit ingredients
  {
    $lookup: {
      from: "ingredients",
      localField: "ingredient_ids",
      foreignField: "_id",
      as: "ingredients"
    }
  },

  // Ausgabe-Felder festlegen
  {
    $project: {
      title: 1,
      author: 1,
      category: "$category.name",
      ingredients: {
        $map: {
          input: "$ingredients",
          as: "ing",
          in: {
            name: "$$ing.name",
            amount: "$$ing.amount",
            unit: "$$ing.unit"
          }
        }
      }
    }
  }
])
```

### Erklärung

Die Pipeline startet in der `recipes`-Collection. Im ersten `$lookup` werden die Kategorien anhand der `category_id` aus der `categories`-Collection eingebunden und mit `$unwind` von einem Array in ein einzelnes Objekt umgewandelt. Im zweiten `$lookup` werden alle passenden Zutaten aus der `ingredients`-Collection über die `ingredient_ids` (Array-Feld) eingebunden. Mit `$project` wird das finale Dokument strukturiert ausgegeben.


## Phase 3: Die Performance-Analyse (20%)

### `.explain("executionStats")` Befehl

```javascript
db.recipes.explain("executionStats").aggregate([
  {
    $lookup: {
      from: "categories",
      localField: "category_id",
      foreignField: "_id",
      as: "category"
    }
  },
  { $unwind: "$category" },
  {
    $lookup: {
      from: "ingredients",
      localField: "ingredient_ids",
      foreignField: "_id",
      as: "ingredients"
    }
  }
])
```

### Metriken

| Metrik | Wert (Beispiel mit kleinen Daten) |
|---|---|
| `totalDocsExamined` | 3 (recipes) + 2 (categories) + 8 (ingredients) = **13** |
| `nReturned` | **3** |
| `executionTimeMillis` | **~5–20 ms** |

> 📸 **Screenshot**: `.explain("executionStats")` Output in MongoDB Compass → hier einfügen.

### Fazit – Warum ist das ein Flaschenhals?

Bei jedem Lesevorgang müssen **alle drei Collections** durchsucht werden. MongoDB führt für jeden `$lookup` einen separaten Collection-Scan durch – ohne Index werden dabei **alle Dokumente jeder Collection gelesen**, unabhängig davon, wie viele am Ende gebraucht werden. Mit wachsenden Datenmengen steigt `totalDocsExamined` linear: Bei 10'000 Rezepten mit je 10 Zutaten müssten über **100'000 Dokumente** gelesen werden, um nur eine Handvoll zurückzugeben. Das Verhältnis `totalDocsExamined / nReturned` wird immer schlechter – das ist der klassische N+1-Flaschenhals, der aus der relationalen Denkweise stammt und in MongoDB besonders teuer ist, weil Joins nicht nativ optimiert sind.

## Phase 4: Der Paradigmenwechsel (Design) (20%)

### Neue JSON-Struktur (Embedded Design)

```json
{
  "_id": "r1",
  "title": "Spaghetti Carbonara",
  "author": "Mario",
  "category": {
    "name": "Pasta",
    "description": "Italienische Nudelgerichte"
  },
  "ingredients": [
    { "name": "Spaghetti", "unit": "g", "amount": 200 },
    { "name": "Speck", "unit": "g", "amount": 100 },
    { "name": "Ei", "unit": "Stück", "amount": 2 }
  ],
  "created_at": "2025-01-15",
  "servings": 2
}
```

### Begründung (~150 Wörter)

Die Kategorie wurde **eingebettet (embedded)**, weil jedes Rezept genau eine Kategorie hat (1-to-1) und die Kategorie beim Lesen eines Rezepts immer mitgelesen wird. Da Kategorienamen sich selten ändern, ist der Aufwand bei einer Aktualisierung (Write) vernachlässigbar klein im Verhältnis zum Lesegewinn.

Die Zutaten wurden ebenfalls **eingebettet**, weil es sich um eine 1-to-Few Beziehung handelt: Ein Rezept hat typischerweise 3–15 Zutaten – eine überschaubare, stabile Menge. Zutaten existieren nicht unabhängig von ihrem Rezept und werden immer zusammen mit dem Rezept abgefragt (Read-to-Write Ratio stark auf Read ausgerichtet). Ein separates Referenzieren würde bei jedem Lesevorgang zwei zusätzliche Lookups erzwingen, ohne einen nennenswerten Mehrwert zu liefern.

Durch dieses Design wird das **gesamte Dokument in einem einzigen Lesevorgang** aus der Datenbank geladen – ohne Joins, ohne mehrere Collection-Scans. Das entspricht dem MongoDB-Prinzip: *Data that is accessed together, should be stored together.*

### Metriken (Neu)

| Metrik | Phase 3 (relational) | Phase 5 (embedded) |
|---|---|---|
| `totalDocsExamined` | **13** (3 Collections) | **3** (1 Collection) |
| `nReturned` | **3** | **3** |
| `executionTimeMillis` | **~15 ms** | **~1 ms** |

> 📸 **Screenshot**: `.explain("executionStats")` der neuen Collection → hier einfügen.

### Vergleich & Interpretation

Das neue embedded Design reduziert `totalDocsExamined` von **13 auf 3** – ein Rückgang um ~77%. Die `executionTimeMillis` sinkt drastisch, da nur noch **eine einzige Collection** gelesen wird, ohne `$lookup`-Joins. Bei grossen Datenmengen (z.B. 10'000 Rezepte) würde der Unterschied noch extremer ausfallen: Das relationale Design müsste über 100'000 Dokumente scannen, das embedded Design genau so viele, wie zurückgegeben werden. Das Re-Design hat sich klar gelohnt.
