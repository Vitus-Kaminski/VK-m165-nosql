## Phase 2 – Das relationale Erbe {#phase-2}

> **Ausgangslage:** Der vorherige Entwickler hat MongoDB wie eine SQL-Datenbank genutzt. Die Daten sind auf drei Collections verteilt: `recipes`, `ingredients` und `categories`.

### 2.1 Importierte Daten (Setup)

Folgende JSON-Daten wurden in drei separate Collections importiert:

**Collection: `recipes`**
```json
[
  { "_id": "r1", "title": "Spaghetti Carbonara", "author": "Mario",
    "category_id": "c1", "ingredient_ids": ["i1", "i2", "i3"] },
  { "_id": "r2", "title": "Avocado Toast", "author": "Sara",
    "category_id": "c2", "ingredient_ids": ["i4", "i5"] },
  { "_id": "r3", "title": "Caesar Salad", "author": "John",
    "category_id": "c2", "ingredient_ids": ["i6", "i7", "i8"] }
]
```

**Collection: `ingredients`**
```json
[
  { "_id": "i1", "name": "Spaghetti",       "unit": "g",       "amount": 200 },
  { "_id": "i2", "name": "Speck",           "unit": "g",       "amount": 100 },
  { "_id": "i3", "name": "Ei",              "unit": "Stück",   "amount": 2   },
  { "_id": "i4", "name": "Avocado",         "unit": "Stück",   "amount": 1   },
  { "_id": "i5", "name": "Toastbrot",       "unit": "Scheiben","amount": 2   },
  { "_id": "i6", "name": "Römersalat",      "unit": "g",       "amount": 150 },
  { "_id": "i7", "name": "Parmesan",        "unit": "g",       "amount": 50  },
  { "_id": "i8", "name": "Caesar Dressing", "unit": "ml",      "amount": 60  }
]
```

**Collection: `categories`**
```json
[
  { "_id": "c1", "name": "Pasta",       "description": "Italienische Nudelgerichte" },
  { "_id": "c2", "name": "Vegetarisch", "description": "Fleischlose Gerichte"       }
]
```

---

### 2.2 Aggregation-Pipeline (Code)

```js
db.recipes.aggregate([

  // Schritt 1: categories einbinden (JOIN über category_id)
  {
    $lookup: {
      from: "categories",
      localField: "category_id",
      foreignField: "_id",
      as: "category"
    }
  },
  { $unwind: "$category" },

  // Schritt 2: ingredients einbinden (JOIN über ingredient_ids-Array)
  {
    $lookup: {
      from: "ingredients",
      localField: "ingredient_ids",
      foreignField: "_id",
      as: "ingredients"
    }
  },

  // Schritt 3: Ausgabe strukturieren
  {
    $project: {
      title: 1,
      author: 1,
      category: "$category.name",
      ingredients: {
        $map: {
          input: "$ingredients",
          as: "ing",
          in: {
            name:   "$$ing.name",
            amount: "$$ing.amount",
            unit:   "$$ing.unit"
          }
        }
      }
    }
  }
])
```

---

### 2.3 Erklärung der Pipeline

Die Pipeline startet in der `recipes`-Collection. Im ersten `$lookup` werden die Kategorien anhand der `category_id` aus der `categories`-Collection eingebunden – `$unwind` wandelt das resultierende Array in ein einzelnes Objekt um. Im zweiten `$lookup` werden alle passenden Zutaten aus der `ingredients`-Collection über das Array-Feld `ingredient_ids` geladen. Mit `$project` wird das finale Dokument sauber strukturiert ausgegeben.

## Phase 3 – Die Performance-Analyse {#phase-3}

> **Ziel:** Messen, wie viele Dokumente MongoDB tatsächlich lesen muss – und warum das bei grossen Datenmengen zum Problem wird.

### 3.1 Ausgeführter Befehl

```js
db.recipes.explain("executionStats").aggregate([
  {
    $lookup: {
      from: "categories",
      localField: "category_id",
      foreignField: "_id",
      as: "category"
    }
  },
  { $unwind: "$category" },
  {
    $lookup: {
      from: "ingredients",
      localField: "ingredient_ids",
      foreignField: "_id",
      as: "ingredients"
    }
  }
])
```

---

### 3.2 Metriken

| Metrik | Wert | Bedeutung |
|---|---|---|
| `totalDocsExamined` | **6** | Alle Dokumente aller Collections wurden gelesen |
| `nReturned` | **3** | Nur 3 Rezepte wurden zurückgegeben |
| `executionTimeMillis` | **6 ms** | Ausführungszeit (bei 6 Dokumenten bereits 6ms) |

### 3.3 Fazit – Warum ist das ein Flaschenhals?

Bei jedem Lesevorgang müssen **alle drei Collections vollständig durchsucht** werden. MongoDB führt für jeden `$lookup` einen separaten Collection-Scan (COLLSCAN) durch – ohne Index werden dabei alle Dokumente jeder Collection gelesen, unabhängig davon, wie viele am Ende gebraucht werden.

Das Verhältnis `totalDocsExamined / nReturned` = **6 / 3 = 2** ist hier noch harmlos. Mit wachsenden Datenmengen explodiert dieses Verhältnis: Bei 10'000 Rezepten mit je 10 Zutaten müssten über **100'000 Dokumente** gelesen werden, um nur eine Handvoll zurückzugeben. Das ist der klassische **N+1-Flaschenhals**, der aus der relationalen Denkweise stammt und in MongoDB besonders teuer ist, weil Joins nicht nativ optimiert sind.

## Phase 4 – Der Paradigmenwechsel (Design) {#phase-4}

> **MongoDB-Prinzip:** *„Data that is accessed together, should be stored together."*

### 4.1 Neue JSON-Struktur (Embedded Design)

Statt drei Collections → **ein einziges Dokument** pro Rezept:

```json
{
  "_id": "r1",
  "title": "Spaghetti Carbonara",
  "author": "Mario",
  "category": {
    "name": "Pasta",
    "description": "Italienische Nudelgerichte"
  },
  "ingredients": [
    { "name": "Spaghetti", "unit": "g",     "amount": 200 },
    { "name": "Speck",     "unit": "g",     "amount": 100 },
    { "name": "Ei",        "unit": "Stück", "amount": 2   }
  ],
  "servings": 2,
  "created_at": "2025-01-15"
}
```

---

### 4.2 Begründung (~150 Wörter)

**Was wurde eingebettet und warum:**

Die **Kategorie** wurde eingebettet (embedded), weil jedes Rezept genau eine Kategorie hat (1-to-1-Beziehung) und die Kategorie beim Lesen eines Rezepts immer mitgelesen wird. Da Kategorienamen sich selten ändern, ist der Schreibaufwand bei einer Aktualisierung vernachlässigbar klein im Verhältnis zum Lesegewinn.

Die **Zutaten** wurden ebenfalls eingebettet, weil es sich um eine **1-to-Few**-Beziehung handelt: Ein Rezept hat typischerweise 3–15 Zutaten – eine überschaubare, stabile Menge. Zutaten existieren nicht unabhängig von ihrem Rezept und werden immer zusammen mit dem Rezept abgefragt. Das **Read-to-Write Ratio** ist stark auf Lesen ausgerichtet (Nutzer lesen Rezepte viel öfter als sie erstellt oder geändert werden). Ein separates Referenzieren würde bei jedem Lesevorgang zwei zusätzliche `$lookup`-Joins erzwingen, ohne Mehrwert zu liefern. Durch Embedding wird das **gesamte Dokument in einem einzigen Lesevorgang** geladen – kein Join, kein zweiter Collection-Scan.

---

### 5.5 Vergleich & Interpretation

Das neue Embedded-Design reduziert `totalDocsExamined` von **6 auf 3** – bei unserem kleinen Testdatensatz. Entscheidend ist aber die **Skalierung**: Das alte Design musste bei 3 Rezepten bereits 3 Collections und 6 Dokumente scannen, weil jeder `$lookup` eine separate Collection-Suche auslöst. Das neue Design liest genau so viele Dokumente, wie zurückgegeben werden (`totalDocsExamined = nReturned`), unabhängig von der Datenmenge. Bei 10'000 Rezepten würde das relationale Design über 100'000 Dokumente scannen – das embedded Design exakt 10'000. Das Re-Design hat sich klar gelohnt.
