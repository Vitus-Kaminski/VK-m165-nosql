### Fragen Phase 1

**Was ist das Hauptmerkmal einer Time-Series Database (TSDB) im Vergleich zu einer klassischen relationalen Datenbank?**

Eine TSDB speichert jeden Datenpunkt zusammen mit einem Zeitstempel und ist für das extrem schnelle sequenzielle Schreiben und zeitbasierte Abfragen optimiert. Eine klassische relationale Datenbank hingegen ist für flexible Abfragen über beliebige Dimensionen konzipiert, nicht speziell für zeitlich geordnete Datenreihen.

**Warum ist es in einer modernen Cloud-Umgebung mit hunderten Servern eine schlechte Idee, sich auf Terminal-Logs zu verlassen?**

Bei hunderten von Servern müsste man sich manuell auf jede einzelne Instanz einloggen, um Logs zu lesen – das ist schlicht nicht skalierbar. Zusätzlich gehen Logs verloren, wenn eine Instanz abstürzt oder neu gestartet wird, da sie lokal auf dem Server gespeichert sind. Ausserdem gibt es keine Möglichkeit, automatisch Muster oder Anomalien über alle Server hinweg zu erkennen oder Alarme auszulösen.

## Phase 2: Die Instrumentierung (Code) (30%)

### Angepasster Python-Code

```python
import time
import random
from prometheus_client import start_http_server, Counter  # AUFGABE 1

# AUFGABE 2: Metrik erstellen
auth_metric = Counter('auth_attempts_total', 'Anzahl der Logins', ['methode', 'status'])

def process_login():
    methods = ['password', 'oauth_google', 'mfa_token']
    method = random.choice(methods)
    
    # 70% Erfolgsquote
    if random.random() > 0.3:
        status = 'success'
        print(f"[AUTH] Login erfolgreich via {method}.")
    else:
        status = 'error_invalid_credentials'
        print(f"[AUTH] FEHLER: Falsche Daten via {method}!")
    
    # AUFGABE 3: Metrik erhöhen
    auth_metric.labels(methode=method, status=status).inc()

if __name__ == '__main__':
    print("Starte Login Server Simulation...")
    start_http_server(8000)  # AUFGABE 4
    
    while True:
        process_login()
        time.sleep(random.uniform(0.1, 1.0))
```

### Erklärung: Aggregation bei unterschiedlichen Zeitspannen

Bei einer kurzen Zeitspanne (z.B. 5 Minuten) sieht man jeden einzelnen Datenpunkt detailliert – die Kurve wirkt zackig und zeigt alle kurzfristigen Schwankungen. Bei einer langen Zeitspanne (z.B. 1 Stunde) aggregiert Grafana viele Datenpunkte zu Durchschnittswerten zusammen, damit der Graph übersichtlich bleibt – die Kurve wird dadurch deutlich glatter und gleichmässiger.

## Phase 5: Architektur-Reflexion (10%)

**Warum lautet die Target-URL in Prometheus und die Data-Source-URL in Grafana jeweils `localhost`?**

Prometheus, Grafana und das Python-Script laufen alle auf *derselben* EC2-Instanz. Aus Sicht des Servers ist sich selbst immer `localhost` – die Public-IP (`54.227.23.244`) ist nur für den Zugriff von aussen (dem eigenen Laptop) notwendig. Die internen Dienste kommunizieren direkt über das lokale Netzwerk-Interface, ohne den Umweg über das Internet nehmen zu müssen.

**Welchen Vorteil bietet das dimensionale Datenmodell mit Labels gegenüber separaten SQL-Tabellen?**

Mit Labels kann man eine einzige Metrik (`auth_attempts_total`) nach beliebig vielen Dimensionen gleichzeitig filtern und gruppieren (z.B. nach `methode=password` und `status=success`), ohne Daten zu duplizieren. Bei separaten SQL-Tabellen müsste man für jede neue Kombination eine neue Tabelle anlegen und komplexe JOIN-Abfragen schreiben – mit Labels geht das mit einer einzigen PromQL-Abfrage wie `rate(auth_attempts_total{status="success"}[1m])`.

**Woher weiss Prometheus, *wann* ein Ereignis stattgefunden hat?**

Im Pull-Modell fragt Prometheus in regelmässigen Abständen (z.B. alle 15 Sekunden) aktiv den `/metrics`-Endpoint des Python-Scripts ab – dieser Vorgang heisst *Scraping*. In genau dem Moment, in dem Prometheus die Metriken abholt, notiert es automatisch den aktuellen Zeitstempel dazu und speichert ihn zusammen mit dem Messwert in der TSDB. Das Python-Script selbst muss sich also nie um die Uhrzeit kümmern – der Zeitstempel entsteht allein durch den Scrape-Vorgang auf Seite von Prometheus.
